# NAV_TAKEOFF — mission protocol notes

See `README.md` for per-test results tables (all stacks side-by-side).

**Migrated onto `Tier1MissionTestBase`/`MissionItemSpec`** (`tests/mission/conftest.py`) — see `tests/mission/CLAUDE.md` § "Shared Tier 1 infrastructure". Needed one framework addition: `ParamSpec.sentinel_xfail_reason` (defined-param counterpart to `reject_xfail_reason`), since NAV_TAKEOFF is supported everywhere (unlike `do_reposition`/`condition_gate`, whose outright rejection skips every param-level test) — the generic sentinel-tolerated test genuinely hits ArduPilot's NaN-rejection quirk on params 1/3/7, which the pre-migration bespoke tests deliberately treated as observational, not pass/fail.

**Tier 2 rebuilt around root `CLAUDE.md`'s "General testing philosophy for MAV_CMD support"** (2026-09-14, revised same day after user review): every yaw/pitch test is explicitly either an "is it honoured" test (one commanded value, real telemetry assertion, imperative `pytest.xfail(...)` if the accepted-but-ignored condition is observed — `test_takeoff_compat_tracks_yaw`, `test_takeoff_compat_tracks_pitch`) or a characterisation test (edge/out-of-range/sentinel values, observational only — `test_takeoff_obs_with_negative_yaw`/`_overflow_yaw`, `test_takeoff_compat_with_pitch_sentinel`/`_large_pitch`/`_negative_pitch`/`_pitch_overflow`, `test_takeoff_compat_with_yaw_sentinel`), plus two position/trajectory characterisation tests (`test_takeoff_compat_respects_position`, `test_takeoff_obs_ascends_before_lateral_movement`). 13 tests total (was 11). Two design points from the review, now baked into root `CLAUDE.md`'s general philosophy (rules 5/6) as reusable patterns, not one-offs:
- **Every test's detail line states its own pass/fail criterion explicitly** ("PASS if ... : <measured values>" or "Observational (<why> ): <measured values>"), not just raw numbers — a reader shouldn't need to open this file to know what a log line means.
- **`test_takeoff_compat_tracks_pitch` is not gated on `--vehicle-type`** (originally planned, then dropped — the harness can't verify that flag against the real connected vehicle). Instead it sends one value, 10°, chosen because it's an achievable fixed-wing climb-out pitch while comfortably exceeding a hover vehicle's incidental peak pitch (observed 1.1–3.4° across this session's PX4 MC runs) — the measured outcome alone classifies "honoured" vs "ignored" correctly either way, replacing the earlier two-flight low(5°)-vs-high(45°) comparison design. `test_takeoff_compat_respects_position`/`test_takeoff_obs_ascends_before_lateral_movement` follow the same never-gate-on-vehicle-type principle: they run unconditionally and let the observed trajectory speak for itself.

Every test's outcome is logged automatically per root `CLAUDE.md`'s Tier 2 design pattern #7 (`logs/mission_nav_takeoff_tier2_*.log`).

## Parameter storage summary (all stacks)

| Parameter | PX4 (all types) | ArduCopter MC | ArduPlane FW / QuadPlane |
|-----------|-----------------|---------------|--------------------------|
| param1 — Pitch | zeroed (not stored) | stored raw; no bounds enforced | stored raw; no bounds enforced |
| param2 — unused | NaN ok; non-NaN silently zeroed | **NaN REJECTED** — spec violation; use 0.0 | same as ArduCopter |
| param3 — Flags | zeroed (not stored) | zeroed (not stored) | zeroed (not stored) |
| param4 — Yaw | stored; −90°→270°, 450°→90° (normalised) | zeroed (not stored) | zeroed (not stored) |
| x/y — location | stored | stored | stored |
| z — altitude | stored; NaN preserved as "use default" | stored; NaN **REJECTED** (sanity_check) | stored; NaN **REJECTED** (sanity_check) |
| INT32_MAX sentinel | accepted ("use current position") | **NACKED** — spec violation | **NACKED** — spec violation |

**PX4**: identical behaviour across multicopter, fixed-wing, and VTOL (same mission storage code).

**ArduPilot**: `mavlink_int_to_mission_cmd` for NAV_TAKEOFF stores only `cmd.p1 = packet.param1`.
`sanity_check_params` uses `nan_mask = ~(1 << 3)` — only param4 may be NaN; params 1/2/3 must be non-NaN or the upload is rejected with `MAV_MISSION_INVALID_PARAM2` (MAVSDK raises `InvalidArgument`).

**ArduCopter/ArduPlane/QuadPlane**: identical storage behaviour.
ArduPlane does **not** require a home item at seq=0 (no `home_item_for_mission` prepend needed).

## Source comparison: why PX4 zeroes param1 (Pitch) and ArduPlane doesn't (2026-09-13, blind review)

**PX4 structurally cannot store it, on any vehicle type.** `msg/NavigatorMissionItem.msg` (the internal mission-item message) has no pitch field at all — no `pitch_min` or equivalent. `mavlink_mission.cpp`'s `MAV_CMD_NAV_TAKEOFF` upload-parse case copies only `param4` (yaw) into the item; param1 is silently dropped, in the same vehicle-type-independent switch used for MC/FW/VTOL. The download-format case symmetrically writes back only yaw. `mavlink_command_params.hpp`'s `VehicleParamOverrides` table has an entry making param1 *upload-acceptable* for FW/VTOL/MC ("GCS (e.g. QGC) send p1=-1 on MC takeoff, so accept p1 for MC too instead of denying") whose comment claims "p1 (minimum pitch angle) is used by FW and VTOL-FW" — but this doesn't match the mission-item pipeline above; FW's actual minimum-pitch-during-climbout value (`FixedWingModeManager.cpp` → `RunwayTakeoff::getMinPitch()`) is sourced entirely from system parameters (`FW_TKO_PITCH_MIN`, `FW_P_LIM_MIN`), never from the mission item. The mask comment looks stale/aspirational, not descriptive of current behaviour — worth a note upstream if this PR/issue tracker is ever engaged.

**ArduPilot's storage is generic and does work — the pipe exists, ArduPlane uses it, ArduCopter chooses not to.** `Mission_Command` has a reusable `p1` field set unconditionally for NAV_TAKEOFF in the same shared-library conversion used by every vehicle type (no `#if`/runtime branch on either the mavlink→cmd or cmd→mavlink side). ArduPlane's `commands_logic.cpp` genuinely reads it: `auto_state.takeoff_pitch_cd = cmd.p1 * 100`, consumed by `takeoff.cpp`'s climb-pitch logic. ArduCopter's `ModeAuto::do_takeoff()` only reads `cmd.content.location` — `cmd.p1` is untouched, confirming "ignored by multicopters" is a Copter-specific *executor* choice, not a storage gap.

**Implication for the 2026-09-13 ArduCopter anomaly** (param1 *and* location zeroed on a fresh SITL instance — see below): since the shared storage/conversion code is vehicle-type-independent and unconditional, nothing in this source review explains a Copter-specific failure to store either value. This strengthens the "stale/mismatched binary" hypothesis over a genuine ArduPilot behaviour change.

**Yaw (param4) execution — the new Tier 2 PX4 finding, now source-confirmed.** `mission_block.cpp`'s setpoint-conversion `case NAV_CMD_TAKEOFF: case NAV_CMD_VTOL_TAKEOFF:` block unconditionally sets `sp->yaw = NAN` when not already flying, with no vehicle-type guard on that line (the only vehicle-type check in the block gates a *different* condition, `already_flying`, for rotary-wing only) — the exact same "Navigator doesn't handle the yaw reset; FlightTaskAuto handles it" comment already known from the COMMAND_INT path (`navigator_main.cpp`) also applies to the mission-item path. So `test_takeoff_with_yaw`'s (renamed `test_takeoff_compat_tracks_yaw` later the same day) new failure is a real, structural finding that should generalise to FW/VTOL too, not something specific to the MC vehicle type tested.

## ArduPilot-specific storage notes

- **Negative pitch underflow**: param1=−10° is stored as 65526° — uint16 underflow: 65536 − 10.
  This is a storage bug (nonsensical if executed).
- **INT32_MAX NACKed**: both ArduCopter and ArduPlane reject the "use current position" sentinel with `INVALID_ARGUMENT` — a spec violation for `hasLocation` commands.
- **param2 NaN rejected**: spec requires unused params to accept NaN; ArduPilot explicitly disallows it via `sanity_check_params`.
- **Positive out-of-range pitch preserved raw**: 89° and 180° stored as-is — no bounds checking on param1.

**QuadPlane SITL note**: use `--model quadplane` with ROMFS defaults only — specifying `--defaults quadplane.parm` causes SITL to crash after the first TCP connection closes.

## 2026-09-15 `test_takeoff_compat_tracks_altitude` redesigned twice; ArduPlane's real altitude behaviour fully traced

The original "wait for 85% crossing, then sample again after a settle delay" design produced a false NOT SUPPORTED on ArduPlane FW (36.5m vs 20m target, 82% over) for a reason unrelated to param7 itself: **redesign #1** replaced the delay-based sample with watching `mission_raw.mission_progress()` for the mission-item index advancing past the takeoff item (a `NAV_WAYPOINT` at the same altitude was added right after `NAV_TAKEOFF` specifically to give every stack something to hold to). Source-confirmed reason for the original false reading: ArduPlane's `exit_mission_callback()` (`commands_logic.cpp`) switches to RTL the instant a mission with nothing left completes, and RTL climbs toward `RTL_ALTITUDE` (`ArduPlane/config.h`'s `ALT_HOLD_HOME`, default 100m) — a parameter completely unrelated to NAV_TAKEOFF's own `z`. The delay-based sample was reading RTL_ALTITUDE convergence, not param7.

That fix alone narrowed ArduPlane's gap (82% over → 40% *under*) but didn't close it, so root-caused the remainder with a real SITL run: instrumented the test with a continuously-timestamped position trace bracketing the `mission_progress()` transition event, confirming the transition itself fired at **12.0m (60% of the 20m target)** while the aircraft was still climbing at ~7 m/s — ruling out read/subscription lag (which would be well under a second, not enough to explain an 8m/1s+ gap at that climb rate) as the cause.

**Redesign #2's actual finding, fully source-confirmed** (`ArduPlane/takeoff.cpp`): `verify_takeoff()`'s altitude-threshold check (`commands_logic.cpp:607-609`) is OR'd with a second, independent condition — `check_takeoff_timeout_level_off()` — which can mark takeoff complete **before** the altitude threshold is ever crossed. Mechanism: `get_takeoff_pitch_min_cd()` (`takeoff.cpp:310-343`) continuously estimates time-to-target from current climb rate; once that estimate drops to `TKOFF_PLIM_SEC` (`Parameters.cpp`, default **2 seconds**), it starts progressively easing the commanded climb pitch toward level (`takeoff_state.level_off_start_time_ms` set) — a genuine stall-safety feature, not a bug, avoiding a hard nose-up attitude right as the aircraft tops out. If that easing has been running for another full `TKOFF_PLIM_SEC`, `check_takeoff_timeout_level_off()` returns true and the mission item is marked complete regardless of achieved altitude. The observed 12.0m/7m/s trace is fully consistent with this: the level-off clock arming around 6m (≈2s-to-target at that climb rate), firing 2s later at 12m.

**Conclusion**: the transition-based test design is correct and unconfounded (verified by direct measurement, not assumption) — what it reveals is that ArduPlane's own definition of "takeoff done" is *intentionally* looser than "reached the commanded altitude." `param7 (Altitude)` genuinely does gate the climb target (the aircraft was climbing toward 20m, not some fixed/ignored value) but a separate, independent completion path can end the takeoff phase early. This is arguably closer to "partially supported with a documented early-exit condition" than a flat "not supported," but the test's stated criterion (±20% of commanded at the point the stack itself calls takeoff complete) is unmet, so `supported: false` remains the correct verdict for that specific, stated question — the nuance is captured in the `notes` field (`"Marked complete at NN% of target altitude"`) rather than silently smoothed over.

Not yet checked: whether `TKOFF_PLIM_SEC=0` (disabling this path entirely) would make the test pass, which would further confirm the mechanism and might be worth doing as a followup, but wasn't done this session (would require a parameter override on the SITL instance, not just a mission/test change).

Downloaded official prebuilt SITL binaries from `firmware.ardupilot.org/{Copter,Plane}/stable/` (`ArduCopter V4.7.1 (dbe79216)`, `ArduPlane V4.7.1 (dbe79216)`) rather than building from source.

**Real bug found and fixed along the way**: ArduPlane fixed-wing/QuadPlane's SITL never became armable on the release binary (`PreArm: "Arm: 3D Accel calibration needed"`) — `tests/conftest.py`'s `_ardu_model_and_defaults()` was passing `defaults=None` for both models (a comment claimed "a .parm file crashes quadplane SITL"; re-tested against the release binary and it did not crash). Fixed by adding `tests/sitl_defaults/plane_ins_cal.parm` (the same tiny nonzero `INS_ACC*OFFS/SCAL` trick copter.parm/quadplane.parm already use) for plain `plane`, and re-enabling upstream's own `quadplane.parm`. See root `CLAUDE.md` Tier 2 pattern #11 for the general principle this became.

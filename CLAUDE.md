## General testing philosophy for MAV_CMD support

What "support" and "fail" mean, tied strictly to a command's own MAVLink XML description (e.g. NAV_TAKEOFF's — https://mavlink.io/en/messages/common.html#MAV_CMD_NAV_TAKEOFF — "Takeoff from ground / hand. Vehicles that support multiple takeoff modes … should take off using the currently configured mode."). Applies to both `tests/command/` and `tests/mission/`.

1. **Supported is binary, and tied only to what the XML actually states.** For NAV_TAKEOFF that's "the vehicle takes off" — nothing about any individual param. A vehicle that takes off passes, full stop. A stack not honouring one particular param value is neither an incompatibility nor a "partial implementation" — there's no such thing as partial support against a command whose spec text doesn't mention that param's required behaviour.
2. **FAIL means the feature is supported but does something contrary to what the XML states.** Not "does something we didn't expect" — contradicts something the XML actually says. Example: NAV_TAKEOFF's XML doesn't say what lat/lon/alt must be used for, so a stack ignoring them outright is not a FAIL by this rule alone (rule 4 below is the one exception).
3. **Undefined behaviour is characterise-and-record, never pass/fail** — and it's still worth testing, for two reasons: (a) devguide/compliance documentation value, and (b) finding *convergent* behaviour across stacks. If every stack tested does the same undefined thing (e.g. every stack clamps an out-of-range param the same way), that's evidence worth escalating as a candidate spec clarification/limit — not a compliance finding about any one stack, but a signal the spec itself might be usefully tightened. Record findings even when they don't move a single test's pass/fail.
4. **The one exception: a defined, accepted param that execution silently ignores without NACKing is a general spec violation** — reported as a genuine `assert`/FAIL, not softened. Mechanism: Tier 1 already establishes the value was accepted (not NACKed) — that's the precondition for a Tier 2 execution test to run at all (see the Tier 2 design patterns below). If Tier 2 then shows the value has no observable effect, that combination (accepted-but-inert) is itself the evidence — no separate "does it NACK" test is needed; the "is it honoured" execution test doubles as this check by asserting the value took effect. **Report this as a plain FAIL, not `xfail`**, even though the *pattern itself* (silently ignoring an accepted param) is common across stacks, not a one-off bug: a specific test run against a specific stack should say plainly whether that run passed or failed, not pre-soften a real result because the general pattern is known elsewhere (revised 2026-09-14 after review — an earlier version of this rule called for `xfail`; keep the suite from being misread as green when a real compliance question was actually answered "no"). This generalises beyond lat/lon/alt to any defined param (Pitch, Yaw, location — see rule 6's update below) — it is not scoped narrowly to location fields. See `tests/mission/nav_takeoff/test_flight.py::test_takeoff_compat_tracks_yaw`/`test_takeoff_compat_tracks_pitch` for the pattern, and rule 7 below for what a *dependent* test (e.g. an edge-value variant of the same param) should do when this core check already failed.
4a. **A rule-4 "is it honoured" test has two acceptable PASS outcomes, not one — and correlating them is how a genuine compatibility error gets found.** Tier 1 already tells you whether a specific non-sentinel value was NACKed outright; that fact alone doesn't decide the rule-4 test's verdict, because a NACK there is a *legitimate* way for a stack to not support the param (it rejected something it can't act on, per rule 4's own logic run in reverse) — it must not be conflated with, or re-asserted as, the "not honoured" FAIL case. So: PASS if either (a) the upload/command was NACKed (correctly rejects a value it can't support), or (b) it was accepted **and** execution reflects it. FAIL is specifically the third combination — **accepted, not NACKed, yet not honoured at execution** — the actual compatibility error rule 4 exists to catch: the stack should have rejected a value it silently cannot act on. Implement this as one small helper correlating `nacked` and `ok` into a verdict string (`REJECTED (NACKed)` / `SUPPORTED` / `NOT SUPPORTED — COMPATIBILITY ERROR`), reused by every rule-4 test in the file, and assert `ok or nacked` rather than `ok` alone. This generalises rule-4 pattern #1's NACK-only-skip principle: a NACK caught around the upload doesn't just gate whether to *fly* — for a "possibly supported" param specifically, it's also a legitimate terminal PASS outcome in its own right, feeding the same compatibility-summary verdict slot the honoured/not-honoured measurement would otherwise feed. See `tests/mission/nav_takeoff/test_flight.py`'s `_compat_verdict()` and its three callers (`test_takeoff_compat_tracks_yaw`, `test_takeoff_compat_tracks_pitch`, `test_takeoff_compat_respects_position`).
5. **Distinguish "is it honoured" tests from "characterisation" tests for every param, and don't blur them.** Concretely, for a param whose XML text gives it real meaning (e.g. NAV_TAKEOFF's Pitch/Yaw):
   - **"Is it honoured" (rule 4's test)**: use one clearly in-range, unambiguous value. Assert the vehicle's real telemetry (attitude, heading, position — not just "it took off") reflects it — a genuine FAIL if not, per rule 4.
   - **Characterisation (rule 3)**: edge/out-of-range/undefined values — test negative, positive/large, wrap-past-360 (for angular params), and the sentinel — always purely observational (log the outcome, no assertion beyond basic safety like "still reaches altitude"), specifically *because* the spec defines no range or bounds. If the XML ever does define an explicit min/max for a param, out-of-range values there DO get a real assertion (expect NACK or clamping) — the "always observational" rule is a consequence of the spec being silent, not a blanket policy.
   - **Sentinel values**: when the XML defines a sentinel's meaning precisely (e.g. NAV_TAKEOFF param4 NaN = "current system yaw heading mode"), there is still no fixed target to assert against if the outcome is dynamic/context-dependent — characterise by observing, and where the protocol allows re-sending live (COMMAND_INT, not a stored mission item), a useful technique is: set an arbitrary, distinctive non-sentinel value first, confirm it, then re-send with the sentinel and check whether the observed state *changes* — evidence the sentinel is live-processed at all, without needing to predict what it resolves to.
   - **Never gate an "is it honoured" test on `--vehicle-type`, or any other declared/assumed vehicle capability.** The harness cannot verify that flag against the real connected vehicle (MAVSDK can't even auto-detect vehicle type from HEARTBEAT), so a test that skips/branches on it can be silently wrong for whoever runs it. Instead, pick **one** commanded value chosen so the *measured outcome itself* distinguishes "honoured" from "ignored" across every vehicle type the command could plausibly target — e.g. NAV_TAKEOFF's Pitch: 10° is a plausible, achievable climb-out pitch for a fixed-wing aircraft, yet comfortably exceeds what a hover-capable vehicle reaches incidentally under vertical acceleration alone (observed 1.1–3.4° peak in this session's PX4 MC runs) — so `peak_|pitch| >= 10° × margin` correctly classifies either vehicle type with a single flight and no branching. This is strictly better than vehicle-type gating: it can't be fooled by a wrong/missing flag, and it works identically for a vehicle type nobody anticipated when the test was written. See `tests/mission/nav_takeoff/test_flight.py::test_takeoff_compat_tracks_pitch`.
6. **Testing lat/lon/alt specifically (a template for any param the XML leaves unspecified)**: since NAV_TAKEOFF's own prose says nothing about how they're used, every one of the following is a characterisation test (rule 3), except where explicitly marked. As with rule 5's pitch example, don't gate any of these on `--vehicle-type` — run them unconditionally and let the observed result classify the vehicle, since e.g. "does it ascend before moving sideways" is itself a well-formed, informative observation for a vehicle that turns out not to hover (it simply shows lateral movement starting at/near ground level):
   - Are the values used at all — does setting them actually move the vehicle there?
   - Is altitude respected specifically (as distinct from lat/lon)?
   - **Is lat/lon respected specifically — this is actually rule 4's "is it honoured" test, not characterisation** (revised 2026-09-14): although NAV_TAKEOFF's own prose is silent, the MAVLink XML schema tags location-bearing params with a shared `hasLocation`/`isDestination` convention used identically by every command that has one, including NAV_WAYPOINT — read under that shared, spec-level convention, "go to this point" is the natural meaning, not an open question. Treat it exactly like Pitch/Yaw: assert the vehicle travels to the commanded point within tolerance, FAIL if it doesn't. See `tests/mission/nav_takeoff/test_flight.py::test_takeoff_compat_respects_position`.
   - Does a vertically-capable vehicle ascend to some height before any horizontal movement (a safety expectation, not a spec requirement) — this one stays pure characterisation; there is no shared XML convention establishing an ascent-order requirement the way there is for "does lat/lon mean go-here".
   - Does it move at an angle (combined climb+transit) or handle altitude and position as separate sequential moves?
   - What happens with the sentinel (INT32_MAX for lat/lon, NaN for altitude) — ascend in place, or something else? (Still characterisation: the sentinel's own meaning is spec-defined, but the resulting trajectory/precision isn't.)
   - **If the param is accepted but its value is provably never used, does the stack NACK a non-sentinel value?** Not doing so is rule 4's spec violation — a genuine FAIL, per rule 4's 2026-09-14 revision.
7. **A test whose own question is moot because a *different* test already showed a prerequisite doesn't work reports NA, not FAIL or a re-run of the same finding.** Concretely: an edge-value or sentinel variant of a rule-4 "is it honoured" param (e.g. NAV_TAKEOFF's negative/overflow Yaw, given `test_takeoff_compat_tracks_yaw` already established whether Yaw is tracked at all) should not independently assert-and-FAIL the same underlying fact a second time under a different name, nor should it silently skip without saying why. Cache the core "is it honoured" probe's result (module-level memoisation — it flies once, regardless of which dependent test triggers it first or whether the core test runs at all in a given selection) and have every dependent test consult it: if the prerequisite failed, mark NA (`pytest.skip("NA: ...")` — the `"NA: "` prefix is a recognised marker, see `tests/flight_helpers.py`'s `_tier2_auto_record`) and skip immediately, without flying; only proceed to the dependent test's own distinct question once the prerequisite is confirmed working. See `tests/mission/nav_takeoff/test_flight.py`'s `_check_yaw_tracked`/`_check_pitch_tracked` and their callers. **The same caching helper also applies when two *independent* tests (not a prerequisite/dependent pair) need the identical mission and only differ in what they read back from the one flight** — e.g. "is the commanded position honoured" (a `_compat` test reading final position) and "does altitude lead lateral movement" (an `_obs` test reading the trajectory) against the same explicit-target NAV_TAKEOFF mission: flying it twice for two different reads is the same wasted arm/climb/RTL/land cycle rule 7 already flags, just without a pass/fail dependency between the two callers. See `_check_position_tracked` and its two callers (`test_takeoff_compat_respects_position`, `test_takeoff_obs_ascends_before_lateral_movement`) — added 2026-09-15 after a review of this file's flight efficiency found the two were flying the identical mission separately for no reason.
8. **Every Tier 2 test name carries a category word as its 3rd word (`test_<cmd>_<category>_<rest>`, e.g. `test_takeoff_compat_tracks_yaw`), not a trailing suffix**, so the category sorts and scans together across a whole file's test list instead of being buried at the end of each name (revised 2026-09-15 — an earlier version of this rule put the category last, as `test_takeoff_tracks_yaw_compat`; moved forward after review so `_compat`/`_info`/`_obs` tests visibly group when test names are listed alphabetically or in `pytest -v` output). The three category words: `compat` (feeds the "Compatibility summary" appended after the main table: a real PASS/FAIL/NA verdict on "is this param supported", via `tests/flight_helpers.py`'s `record_tier2_param_verdict(request, "param1 (Pitch)", "SUPPORTED")`-style call from whichever single test is the definitive check for that param — call it once per param, not from every test that happens to touch it), `info` (PASS/FAIL but not measuring the command's own param compliance — pair with the `"(Information)"` prefix on its detail), or `obs` (characterisation only, rule 3, no compatibility verdict). See `tests/mission/nav_takeoff/test_flight.py` for a fully-worked example of all three, including the compatibility summary's rendered output.
9. **`test_protocol_` is reserved for genuine protocol-mechanics tests — generic across MAV_CMDs, not a per-command tag** (established 2026-09-17, correcting an earlier, wrong assumption that it was simply a "this is a Tier 1 test" marker). These live in the shared, command-agnostic files (`tests/command/test_protocol.py`; the mission-side equivalents in `tests/mission/test_mission_client.py`/`test_mission_server.py`/`test_protocol_conformance.py`), and are prefixed `test_protocol_<mechanics-description>` (e.g. a hypothetical test comparing COMMAND_LONG vs COMMAND_INT ACK-handling equivalence would be `test_protocol_command_long_vs_int_<rest>`). **A test whose subject is one specific MAV_CMD's own behaviour is named after that command instead, never `test_protocol_`** — `test_<full_command_dir_name>_<rest>` (e.g. `test_do_reposition_param1_speed_preserved`, `test_nav_takeoff_param1_pitch_preserved`), and when the test specifically distinguishes COMMAND_LONG-vs-INT encoding for that command, the message-type token follows directly: `test_do_reposition_command_long_nan_latlon`. **A test inherited unchanged from `Tier1MissionTestBase`/`Tier1CommandTestBase` (identical across every command built on it) is exempt from the command-name prefix** — the class/`SPEC` it's attached to already establishes which command, so the name should instead describe the real differentiating property under test (`test_defined_param_sentinel_tolerated` vs. `test_undefined_param_sentinel_accepted` — "defined"/"undefined" is genuine signal, not filler). **The overriding principle is purpose, not mechanical uniformity**: add a prefix token only where it actually differentiates a test's subject or scope — don't prepend one just to tag every test the same way for its own sake. Rolled out 2026-09-17 to `mission/nav_takeoff`, `mission/do_reposition`, `command/do_reposition`, `command/do_set_global_origin`, `command/nav_land`, `command/do_set_mission_current` (~123 test renames total, plus every README/CLAUDE.md cross-reference); `command/nav_takeoff`, `command/external_wind_estimate`, and `mission/condition_gate` still need the same treatment — see `TESTING_PATTERNS.md`.

## Conventions

- **Test logs vs. reports**: the automated Tier 1/Tier 2 per-MAV_CMD report (`tests/report.py`, see Tier 2 design pattern #7 below) goes to `reports/` (gitignored). Everything else — bespoke survey/tool output (`test_survey.py`, `test_ack_uniqueness.py`), SITL console redirection, and any other hand-written log — still goes to `logs/` at the repo root (e.g. `logs/test_arducopter_20260524.log`), which is also gitignored (`*.log`).
- **Live pytest logging is opt-in, not default**: `pytest.ini` sets `log_cli_level`/`log_cli_format` but deliberately does not set `log_cli = true` — a bare `pytest tests/...` run stays quiet (pass/fail only). Pass `--log-cli-level=INFO` (as every command in this file and the READMEs does) to see `log.info`/`log.warning` output live; when running tests, use this flag. **Never** make a flight stack's own SITL console/shell output (ArduPilot's `Starting sketch '...'`/`bind port ... for SERIAL...` banner, PX4's `pxh>` shell spam, etc.) reach this stream — `_manage_ardupilot_sitl`/`_manage_px4_sitl` in `tests/conftest.py` already redirect the SITL subprocess's stdout/stderr straight to its own file under `logs/` and only ever read that file back for a membership check (e.g. `"Waiting for connection" in log_path.read_text()`), never to echo its content into `log.info()`; keep it that way — SITL console noise belongs only in its own per-run log file, never in pytest's log stream at any verbosity.
- **README synchronisation**: the root `README.md` and `tests/mission/README.md` must both be kept up to date whenever autopilot behaviour changes, new tests are added, or test result counts change.
  The subfolder README carries the detailed per-frame comparison tables; the root README carries the high-level summary.
  Update both together.
- **Test timeouts**: every test must be protected against hanging indefinitely.
  Use `asyncio.wait_for()` (or `asyncio.timeout()`) inside async helpers to guard individual MAVLink round-trips.
  The global `pytest-timeout` default (120 s in `pytest.ini`) covers the whole test function as a safety net.
  Override with `@pytest.mark.timeout(N)` (or a module-level `pytestmark`) only for tests that legitimately need more:
  - Protocol tests (mission upload/download, COMMAND_ACK): no override needed — completes well within 120 s.
  - Command protocol class-based tests (`TestCommandProtocol`, `TestNavTakeoffCommand`): `@pytest.mark.timeout(300)`.
  - Flight tests (`test_flight.py`): `pytestmark = pytest.mark.timeout(360)`.
  - Command survey (`test_survey.py`): `@pytest.mark.timeout(900)`.
  - Command ACK-uniqueness survey (`test_ack_uniqueness.py::TestCommandAckUniqueness`): `@pytest.mark.timeout(900)` — 168 commands × a fixed 1.5 s post-send listen window each (it cannot early-exit on the first ACK like `test_survey.py` does, since it must wait out the window to catch a delayed duplicate).
    When adding a new test that could legitimately exceed 120 s, add the override and document the reason.
- **MAVLink spec discrepancies**: When observed flight-stack behaviour contradicts the official MAVLink documentation (mavlink.io), note the discrepancy explicitly in:
  1. The test log output (`log.warning` with "DOC DISCREPANCY:" prefix).
  2. The relevant README results table with a footnote.
  3. CLAUDE.md under the affected autopilot's behaviour section.
     Open an issue at https://github.com/mavlink/mavlink/issues if the spec is demonstrably wrong or ambiguous.
     Do not assume the stack is wrong — it may be that the spec lags the implementation.
  Reserve this for a genuine contradiction of the documented spec. A stronger/more mechanistic explanation of behaviour a doc already describes correctly (e.g. source confirms *why* a value is "ignored") is not a discrepancy — don't flag it as one.
- **Tier 2 (live flight) test design patterns** — applies to both `tests/command/*/test_flight.py` and `tests/mission/*/test_flight.py`:
  1. **Tier 1 findings gate whether Tier 2 *runs*, not whether it's *written* — and the only thing that legitimately gates a skip is an explicit protocol-level NACK.** An upload/command rejection is the one outcome a test can know unambiguously, at runtime, on any stack, any frame, forever — so it's the only basis for `pytest.skip`. Anything else Tier 1 observes about an *accepted* item or command — a param round-tripping unchanged, normalised to a canonical form, zeroed, or altered to something else entirely — is not a legitimate skip basis, even when source reading strongly suggests the field is dead (e.g. "confirmed never read by this handler"). A source-derived claim about *why* a value changed is not something the test itself measured, doesn't hold generically across stacks/frames/future versions, and specifically must never be used to justify skipping execution verification — it's fine as commentary in this file or a README, never as the runtime skip condition. Concretely: **always write the Tier 2 test**; a later stack version or a different vehicle/variant might reject where this one silently accepts, or accept where this one alters, and the test should already exist to catch that. What changes at runtime is that the test must **detect an actual NACK and skip cleanly** (`pytest.skip`, not error or fail, and not simply omitted from the file) rather than attempt to fly something Tier 1 already proved impossible. Two shapes, depending on where the NACK bites: (a) the whole command is rejected — the flight test's own mission upload attempt catches the NACK and skips (see `tests/mission/condition_gate/test_flight.py`'s upload try/except); (b) a specific param probe is NACKed but the command itself flies fine — use the existing "conditional Tier 2 pattern" (`tests/mission/CLAUDE.md`): an inline Tier-1-style probe at the top of the Tier 2 test itself decides whether to proceed (any accepted outcome, including altered/normalised/zeroed) or skip (NACK only), and when proceeding, assert against whatever the probe actually observed as stored — not the value the test intended to upload or a value assumed from source reading — so the flight portion activates automatically the moment underlying support changes and the assertion never depends on an inference the test didn't itself verify. Exception: no meaningful cost to running it anyway (e.g. it falls out for free from a case already being flown) — then there's no reason to gate it at all.
  2. **Minimal-safe padding, tuned from real telemetry, not guessed generously.** A live flight test needs enough slack in timeouts and mission geometry to establish a reliable baseline on the first attempt (SITL startup jitter, climb rate, and control-loop settling are all somewhat unpredictable before you've seen real telemetry) — but once it has actually passed and you have real numbers, tighten constants toward what was observed plus a modest margin (~20%, not 2x). An overly generous tolerance both wastes test time and can mask a real behavioural regression. Log the evidence that would inform tightening (sample counts, completion timestamps, achieved margins) at `INFO` level on every run, even though it isn't asserted on — so the next person tuning the test has real data instead of needing to add instrumentation first.
  3. **Derive timing/distance budgets from measured parameters, not flat guesses tuned to one stack.** Where a run-specific figure needed for a wait/timeout is cheaply queryable at runtime (e.g. a cruise-speed parameter), read it and scale the budget from it, rather than hardcoding a number that only holds for the specific stack/config it was last tuned against — a slower-configured stack then gets proportionally more time automatically instead of the test needing hand-retuning per stack. For the one part that genuinely can't be cheaply measured (e.g. climb rate over MAVLink), use a single flat, clearly-named, conservative constant, isolated so it's the one dial to widen if a slower stack needs more room — don't fold it into an unnamed total-duration guess.
  4. **Make cross-stack timing risk self-diagnosing and externally tunable.** Constants tuned against telemetry from one stack risk being too tight the first time the same test runs against a different (e.g. slower-climbing) stack — which looks identical to a real behavioural regression unless the test says otherwise. Two cheap mitigations: (a) expose the constant(s) most likely to need stack-specific widening as an environment-variable override with the tuned value as the default (`float(os.environ.get("SOME_ALLOWANCE_S", "25.0"))`), so a future run can pass a larger value with no code edit; (b) when an assertion depending on "the mission reached point X" fails, check whether the sample data itself suggests the time budget simply ran out before getting there (last sample near the end of the budget, progress well short of X) and prefix the failure message with something like "likely insufficient sampling time for this stack, not necessarily a behavioural finding" — so whoever (or whatever) investigates next isn't misled into debugging the flight stack when the fix is widening a constant. See `tests/mission/condition_gate/test_flight.py`'s `_timing_caveat()` helper and `CONDITION_GATE_CLIMB_ALLOWANCE_S` for the concrete pattern.
  5. **Blind source review before comparing to results — do this the first time a new Tier 2 test is added, and again the first time it runs against a new stack.** Before looking at telemetry (or independently of having already looked), read the relevant source and write down what you expect to happen, mechanism and all. Then compare to what actually happened. The point isn't to re-confirm the headline pass/fail — it's to catch (a) things the test doesn't actually exercise the way you assumed, and (b) real behaviour worth documenting for devguide readers even though it doesn't affect compliance. Record findings tersely, here or in the command's own CLAUDE.md. Example: `tests/mission/condition_gate/`'s crossing-point check. Blind reading of `mission_block.cpp`'s `NAV_CMD_CONDITION_GATE` branch shows the trigger is `dot(vehicle_pos - gate_pos, normalize(next_real_waypoint_pos - gate_pos)) >= 0` — a plane through the *gate's own position*, perpendicular to the vector from the **gate to the next real waypoint** (skipping intervening `DO_*` items), not perpendicular to the inbound path and not at the gate's simple path-projection. For an off-path gate these differ measurably: in `test_flight.py`'s geometry (gate 25 m east of a straight-north leg, naive path-perpendicular projection at north=120 m) the true trigger plane, worked out from that dot product, is at north≈111 m — about 9 m earlier. Observed telemetry (speed-threshold detection at ~116 m, averaged over 5 runs) is consistent with this once ~5 m of deceleration lag between the true trigger and the detectable speed drop is added back — i.e. two independent, individually-predictable effects, not one unexplained number. Not a compliance issue (PX4 gates the mission correctly), but mavlink-devguide PR #761's prose/diagram ("perpendicular to the gate location") is a simplification that doesn't distinguish "perpendicular to the path" from "perpendicular to gate→next-waypoint" — worth sharpening if that PR is revisited.
  6. **"Accepted but ignored, without a NACK" is a general spec violation, reported as a plain FAIL — see "General testing philosophy" § rules 4/7 above for the full reasoning, the NA-gating for dependent tests, and why this is no longer `xfail`.** Every "is it honoured" test for a defined param is this check; no separate NACK-specific test is needed.
  7. **Every test's outcome (Tier 1 and Tier 2 alike) is written to one combined, unified report per MAV_CMD — `tests/report.py`, redesigned 2026-09-16 per the user's own explicit request.** A report is keyed by `(protocol, cmd_name)` (`"mission"`/`"command"`, e.g. `"NAV_TAKEOFF"`) and contains whichever tier(s) actually ran in this pytest session — Tier 1 only if only `test_protocol.py`/`test_command.py` ran, Tier 2 only if only `test_flight.py` ran, both combined into one file if both ran (e.g. `pytest tests/mission/condition_gate/`). Two files, sharing one filename prefix, written to **`reports/`** (gitignored — regenerated every run, not durable data): `reports/<protocol>_<cmd_name>_<autopilot>_<vehicle>_<version>_<timestamp>.log` (human-readable, both tiers' tables + the compatibility summary) and `...json` (the mavlink-compat-data-shaped export, described below). Both rewritten unconditionally after every test that touches this report, not just once at session end — a run that hangs or is force-killed still leaves whatever ran so far on disk. The pre-2026-09-16 split (`logs/<protocol>_<name>_tier1_...log` written once at Tier 1 class teardown, `logs/<protocol>_<name>_tier2_...log` rewritten per Tier 2 test) is gone — `tests/report.py` is now the only place either tier writes a results file.
      - **Tier 1's own facts are captured automatically, with zero per-command code.** `Tier1MissionTestBase`/`Tier1CommandTestBase` (`tests/mission/conftest.py` / `tests/command/conftest.py`) call `report.declare_command()`/`declare_params()` once per subclass (`__init_subclass__`, reading the command's own `SPEC.params`) and `report.record_tier1_result()`/`record_compat_fact()`/`record_command_fact()` from their existing generic sentinel/non-sentinel/baseline-support tests — the same three tests every migrated command already had. This means **every command using the shared Tier 1 base classes gets a report and a schema-shaped JSON export automatically**, including one with no Tier 2 test at all (e.g. `do_reposition`, rejected everywhere at Tier 1 — its report correctly shows `"supported": false` at the frame level, `"basis": "testing"`, `"last_checked_version"` set, and no `params`/`notes` at all, since a plain `UNSUPPORTED` rejection has nothing further to say and the schema doesn't allow ordinary params under an unconfirmed-supported frame — see the schema-conformance bullet below).
      - **Tier 2's "is it honoured" facts stay explicit calls** (`record_tier2_param_verdict`, `record_compat_json`≡`report.record_compat_fact`, `record_compat_command_supported`≡`report.record_command_fact`, all in `tests/flight_helpers.py` — thin wrappers over `tests/report.py`, kept under their old names so existing Tier 2 call sites didn't need to change) — *which* test is the definitive execution-level check for a given param is inherently a judgement call a generic base class can't make the way it can for Tier 1's mechanical sentinel probes.
      - **The mavlink-compat-data JSON schema is rendered in exactly one place** (`tests/report.py`'s `render_json_doc()`) — a future schema change is a one-function edit, shared by every command in both `tests/mission/` and `tests/command/`, not a per-test-file hunt. A module declares its command's full canonical param-slot list once, at import time (`report.declare_params(protocol, cmd_name, [f"{p.slot}_{p.label}" for p in SPEC.params])`, deriving it from the sibling `test_protocol.py`/`test_command.py`'s own `SPEC` — see `nav_takeoff`/`condition_gate`'s `test_flight.py` for the pattern) so every declared param always renders, `"supported": null` ("not independently tested this run") for any whose test errored out before recording anything, instead of silently vanishing (indistinguishable from "forgot to test it") — and so a Tier-2-only run (no Tier 1 in the same session) still gets the full list.
      - **Adopting the Tier 2 half in a new or existing module costs the same two module-level constants and one import as before**: declare `_CMD_NAME`/`_CMD_ID`, and import `_tier2_auto_record` from `tests.flight_helpers` alongside `require_real_stack` (both `autouse=True` — importing a fixture by name into a test module's namespace is what activates it). Call `record_tier2_detail(request, "...")` only when the default detail (docstring first line, or failure/skip reason) isn't informative enough. The pre-existing bespoke `_write_and_update_readme()` prose-summary writers in `tests/command/nav_takeoff/` and `tests/command/nav_land/` are untouched by this — they serve a distinct purpose (a natural-language behaviour summary for the README) and remain a second, complementary output, not a replacement.
      - **A matching auto-record fixture for *bespoke* Tier 1 files (`_tier1_auto_record`, `tests/report.py`) shipped 2026-09-17**, so a command directory doesn't need its `test_command.py` restructured onto `Tier1CommandTestBase` just to get a report — it costs the identical two-constants-plus-one-import adoption cost as the Tier 2 fixture above, with zero changes to the file's own test bodies or assertions. Rolled out the same day to every command directory that wasn't already covered (`do_reposition`, `do_set_global_origin`, `do_set_mission_current`, `nav_land`), so **reporting coverage across `tests/command/` and `tests/mission/` is now 100%** regardless of whether a given command's Tier 1 checks are hand-written or inherited from `Tier1CommandTestBase`/`Tier1MissionTestBase` (see `tests/command/CLAUDE.md`'s migration-status note for that distinction). Both auto-record fixtures resolve their `(protocol, cmd_name)` key via one shared helper, `report.key_from_module()`.
      - **Schema-conformance fixes (2026-09-17), made after the user compared real tool output against the actual upstream `mavlink-compat-data` schema (`schema/compatibility-entry.schema.json`, fetched via `gh api`, not assumed from memory) and caught three real bugs in `render_json_doc()`**: (1) `basis` had defaulted to `"verified"` — wrong, since the schema reserves that value for a human project maintainer's manual sign-off, never something an automated harness can claim about its own run; every recorder now defaults to `"testing"` (`record_command_fact`'s `basis` kwarg, `tests/report.py`). (2) `params` was rendered under a frame even when that frame's `supported` wasn't the confirmed-implemented object form — the schema only allows an ordinary (non-`"<n>_Empty"`) param there when the command itself is confirmed supported; a reserved `"<n>_Empty"` key is exempt (it carries a protocol-level sentinel fact independent of command support) but every other param is now dropped for an unsupported/unknown frame. (3) `earliest_checked_version` (a lower bound on "added_version: true", i.e. "was already supported by at least this version, don't know how much earlier") was being used unconditionally — it's now used *only* when the command is confirmed supported; every other case (`false`, `null`) uses `last_checked_version` ("still true as of this run") instead, since there's no "when was it added" question to bound when it isn't confirmed added at all. A redundant `notes` field that just restated `supported: false` (e.g. `"UNSUPPORTED"`) was also dropped — a genuinely distinguishing NACK reason (e.g. `DENIED`) is still recorded.

  8. **RTL does not reliably ground a vehicle for cleanup — never blindly disarm afterward regardless of whether it landed. Restart the flight stack instead when it didn't.** Discovered 2026-09-15 investigating ArduPlane FW/QuadPlane's NAV_TAKEOFF Tier 2 cascade (nav_takeoff/CLAUDE.md has the full story): ArduPlane's `RTL_AUTOLAND` defaults to disabled, and a mission with no `DO_LAND_START` item just makes RTL loiter at home forever — it never reaches `LandedState.ON_GROUND`. The old `_rtl_and_land()` waited for that landed state, then called `action.disarm()` *unconditionally* regardless of whether the wait actually succeeded. For a stack that honours an in-air disarm, that crashes the vehicle; ArduPilot's own `AP_Arming_Plane::disarm()` correctly *refuses* a MAVLink-originated disarm while `is_flying()` (a real safety check, not a bug to work around), so the disarm silently no-ops instead — either way the vehicle is left in a broken state (crashed, or armed-and-still-flying) that every subsequent test in the file then inherits, rather than the clean "on the ground, ready to arm" state each test assumes it's starting from. **Fix**: `tests/conftest.py`'s `restart_flight_stack` fixture (session-scoped, returns a synchronous callable) kills and restarts whichever SITL process is active — plus its bridging `mavsdk_server`, since ArduPilot's TCP connection doesn't reliably redial a closed peer the way PX4's UDP one self-heals — reusing the exact same `_start_px4_process()`/`_start_ardupilot_process()` sequence session startup uses (extracted into standalone functions for this reason). `tests/flight_helpers.py`'s `_rtl_and_land()` takes it as an optional second positional argument: pass it and a failed landed-state wait triggers a restart instead of a blind disarm; omit it (existing call sites elsewhere are unaffected) and the old best-effort-disarm behaviour is unchanged — restart is opt-in per Tier 2 module, not a global behaviour change, since plenty of existing modules (anything that already reliably RTL+lands, e.g. PX4 MC) don't need it and a restart costs real wall-clock time (~15-45s) that's wasted when RTL was already going to work. A cold restart is typically *faster* than the alternative it replaces (`RTL_LAND_TIMEOUT_S=120s` of waiting for a landing that will never come), not slower — this is an efficiency win, not just a correctness fix. See `tests/mission/nav_takeoff/test_flight.py` for a fully-worked adoption (every flight-ending `finally` block passes `restart_flight_stack` through).
  9. **When a characterisation test's own failure is ambiguous, but *other* tests in the same file give it real diagnostic power, use that — explicitly, in the detail line, not just implicitly in the reader's head.** `test_takeoff_info_implicit_from_waypoint` (nav_takeoff) asks "does a waypoint-only mission (no explicit NAV_TAKEOFF item) still take off" — on its own, a timeout there is ambiguous: does this frame need an explicit NAV_TAKEOFF item, or does it just not take off at all today (broken SITL, resource contention, anything)? Every *other* test in the same file already answers a strictly easier version of "can this frame take off at all" (using an explicit item), so: (a) run the ambiguous characterisation test **last** in the file (not wherever it happens to fall thematically), after everything that could establish the easier fact already has, and (b) have it check a small module-level flag any of those other tests sets on a successful climb, and route its own failure message through that — "TAKEOFF item is required for this frame" (confirmed) vs. "inconclusive, nothing else got airborne either" (not confirmed) are genuinely different findings, not the same timeout with a shrug attached. See `_explicit_takeoff_confirmed` and its four setters.
  10. **Measure a param's effect at the discrete event that actually reflects it, not a fixed delay afterward — a delay window is exposed to whatever the stack does *next*, which is a different, uncontrolled variable.** `test_takeoff_compat_tracks_altitude` (nav_takeoff, 2026-09-15) originally sampled altitude a fixed 5s after crossing 85% of the commanded value — clean on PX4 MC, but a false NOT SUPPORTED on ArduPlane FW, because ArduPlane autonomously switches to RTL the instant a single-item mission completes, and RTL climbs toward `RTL_ALTITUDE` — an entirely different, unrelated parameter — so the fixed-delay sample was reading that, not the param under test. Fix: subscribe to the protocol's own completion signal (here, `mission_raw.mission_progress()`'s current-item-index advancing — the same event fires whether the mission has one item or many, and needs no added mission item at all for a multi-item mission) and read the value at that instant. **This isn't automatically a full fix** — it only removes confounds from *what runs after* the event; it does not, and cannot, correct for the stack's own completion criterion being looser than the test's stated one (see nav_takeoff's `CLAUDE.md`: ArduPlane can mark takeoff complete via a documented pitch level-off timeout, up to ~40% short of the commanded altitude, by design — a real, separate finding the event-based measurement correctly surfaced instead of masking). When a redesigned measurement still doesn't match expectations, verify with a real instrumented trace (timestamped samples bracketing the event) before assuming lag or a further measurement bug — root-causing nav_takeoff's residual gap this way took one background-sampler-instrumented SITL run and a source read, not more guessing.
  11. **When a flight stack needs special setup just to become flyable at all, isolate that setup in a thin, stack-keyed layer — never let it leak into the test bodies themselves.** Test logic (upload mission, arm, watch for the event under test) should stay identical across every stack; only the *setup* should vary, and only where a stack genuinely demands it. Concrete example: ArduPlane's official SITL binaries ship no `plane.parm` (unlike copter/rover/quadplane, which each get one), so a freshly-booted `--model plane` instance has all-zero `INS_ACC*OFFS/SCAL` and never reports armable (`PreArm: "Arm: 3D Accel calibration needed"`) — confirmed 2026-09-15 against the official ArduPlane 4.7.1 release binary. The fix is not a per-test workaround; it's `tests/conftest.py`'s `_ardu_model_and_defaults()` — one function, keyed on vehicle model, that hands `_manage_ardupilot_sitl` whichever `--defaults=` file (if any) that model needs (`tests/sitl_defaults/plane_ins_cal.parm`, a small checked-in file, for plain `plane`; upstream's own `quadplane.parm`/`copter.parm`/`rover.parm` otherwise). Every Tier 2 test file stays completely unaware this exists. Apply the same discipline to any other stack-specific flyability quirk found later (e.g. VTOL's still-unexplained "arms and starts the mission but never leaves the ground" — see future-work item #10 below): if it turns out to need, say, sustained neutral `manual_control` input to satisfy an RC-presence gate, that belongs in a startup/setup helper keyed on vehicle type, not sprinkled into `_fly_to_altitude_target` or any other individual test.

### MockFlightStack

`tests/mock_flight_stack.py` implements the full MAVLink mission protocol on the drone side via `mavlink_direct`, so all client tests can run against a local loopback mock without a real autopilot.

**Protocol handlers** (all via `drone_system.mavlink_direct`):

| Handler | Receives | Sends |
|---------|---------|-------|
| Upload | `MISSION_COUNT` → `MISSION_ITEM_INT` × n | `MISSION_REQUEST_INT` × n → `MISSION_ACK(SUCCESS)` |
| Download | `MISSION_REQUEST_LIST` | `MISSION_COUNT` → `MISSION_ITEM_INT` × n |
| Clear | `MISSION_CLEAR_ALL` | `MISSION_ACK(SUCCESS)` |
| Capability | `COMMAND_LONG(cmd=512, p1=148)` | `AUTOPILOT_VERSION(capabilities=…)` |
| Command INT | `COMMAND_INT` | `COMMAND_ACK(result, progress)` |
| Command LONG | `COMMAND_LONG` (non-capability) | `COMMAND_ACK(result, progress)` |

**Default behaviour**: accept all frames, store items exactly as received, serve unchanged on download, report `MAV_PROTOCOL_CAPABILITY_MISSION_INT` (bit 2 = 4).
Returns `MAV_RESULT_ACCEPTED (0)` for all COMMAND_INT and COMMAND_LONG by default, except that COMMAND_INT with lat/lon (x/y) values outside the valid range (±90°/±180° × 1e7) returns `MAV_RESULT_DENIED (2)`.
The INT32_MAX sentinel is always valid.

**Configurable parameters** (constructor kwargs):
- `capability_bits` — capabilities bitmask in AUTOPILOT_VERSION response
- `item_request_delay_s` — per-item delay before MISSION_REQUEST_INT (upload)
- `item_response_delay_s` — per-item delay before MISSION_ITEM_INT (download)
- `drop_responses` — `{msg_name: N}` to silently drop first N of that outgoing mission message
- `rejected_frames` — frame values to NACK with UNSUPPORTED_FRAME on upload
- `command_results` — `{cmd_id: MAV_RESULT}` to configure per-command ACK results
- `drop_command_acks` — `{cmd_id: N}` to drop first N COMMAND_ACKs for that command
- `command_in_progress` — `{cmd_id: [p0, p1, ...]}` to emit IN_PROGRESS ACKs before final ACK

**`received_commands`**: list of all received COMMAND_INT and non-capability COMMAND_LONG messages, each as a dict with fields `type`, `command`, `frame` (COMMAND_INT only), `confirmation` (COMMAND_LONG only), `param1`–`param4`, `x`, `y`, `z`.

**Capability response interaction**: the drone mavsdk_server binary also responds to AUTOPILOT_VERSION requests with its own bits (0x2000 = MAV_PROTOCOL_CAPABILITY_MAVLINK2).
`_get_autopilot_capabilities()` OR-combines all responses within a 0.3 s window.

**Legacy-command auto-ACK duplication (`MAV_CMD_REQUEST_AUTOPILOT_CAPABILITIES`, cmd=520)**: discovered via `tests/command/test_ack_uniqueness.py` — the drone-side mavsdk_server binary auto-ACKs this deprecated command itself, in addition to whatever MockFlightStack sends. Confirmed by raw wire inspection: two byte-identical `COMMAND_ACK(cmd=520, result=0)` messages arrive at the GCS even though `received_commands` shows only one incoming `COMMAND_INT` was ever delivered to the Python handler. Same family of behaviour as the AUTOPILOT_VERSION dual-response above — a MAVSDK test-harness artifact, not a flight-stack bug, and it does not occur in standalone mode (a real vehicle is the sole ACK source there). `test_ack_uniqueness.py` excludes cmd 520 from its assertion in mock mode only (`_MOCK_ONLY_KNOWN_DUPLICATES`).

All tests are async (pytest-asyncio, asyncio_mode=auto).

### Autopilot probe (`tests/conftest.py`)

Session-scoped `_autopilot_header` autouse fixture: calls `system.info.get_version()` (firmware version, git hash — reliable) and `system.info.get_product()` (vendor name, best-effort).
ArduPilot stores git hash as ASCII bytes in `flight_custom_version`; the probe ASCII-decodes these.
`suggest_log_filename()` derives log prefix from test path (e.g. `tests/mission/test_frame_types.py` → `mission_frame_types`).

**HEARTBEAT limitation**: MAVSDK intercepts HEARTBEAT internally — vehicle type cannot be auto-detected from HEARTBEAT.
Use `--vehicle-type` CLI option for correct log naming.

**MAVLink enum loading**: `_load_mavlink_enum()` parses the bundled XML submodule at import time.
Falls back to a hardcoded dict with `log.warning` when the submodule is absent.

## MAVSDK plugin choices

- `mission_raw` — GCS tests; maps 1:1 to MISSION_ITEM_INT fields; supports all three mission types.
- `mission_raw_server` — drone/server tests; mirrors MISSION_ITEM_INT on the server side.
- `mavlink_direct` — send/receive raw MAVLink messages.

The high-level `mission` plugin is NOT used — it abstracts away mission_type, geofence, and rally points, making protocol-level testing impossible.

### ArduCopter connection reliability pitfalls

**1. CLOSE-WAIT accumulation** — ArduCopter does not close its TCP socket on abrupt disconnect.
After killing mavsdk_server, port 5760 appears open but ArduCopter is in CLOSE-WAIT and won't heartbeat on new connections.
**Fix**: restart ArduCopter SITL.
Check with `ss -tlnp | grep 5760`.
Do **not** use `nc -z 127.0.0.1 5760` — that creates another CLOSE-WAIT.

**2. Missing / wrong parm file** — ArduCopter silently accepts the TCP connection then panics while loading defaults.
Correct path: `~/github/ArduPilot/ardupilot/Tools/autotest/default_params/copter.parm`.

## CI — running multiple SITL instances concurrently (2026-09-15)

Both flight stacks natively support running several independent SITL instances side by side on one host, with zero simulator-side changes — the only thing standing in the way was this harness's own process-management fixtures assuming exactly one instance (a blind `pgrep -x px4`/`pgrep -x <binary>` kill-everything step, a single hardcoded port set, and a single working/state directory). All of that is now instance-scoped via one new CLI flag, **`--sitl-instance N`** (default 0 — behaves byte-identically to before multi-instance support existed; every path below is opt-in).

### How each stack derives its own port set from an instance number

**PX4 SIH** — confirmed by reading `ROMFS/px4fmu_common/init.d-posix/px4-rc.mavlink` in the actual PX4-Autopilot checkout: every MAVLink port PX4 opens is computed from a single `$px4_instance` shell variable, set via the binary's own `-i N` flag (`px4 --help`: *"px4 instance id to run multiple instances [0...N], default=0"*). Instance N's **offboard/API port** — the one `--drone-address` connects to — is `14540+N`; its GCS-link local port is `18570+N`. `-i N` also auto-bumps `MAV_SYS_ID` (confirmed empirically: instance 1 came up with `MAV_SYS_ID: curr: 1 -> new: 2`), so concurrent instances don't collide on MAVLink system ID either.

**ArduPilot SITL** — confirmed directly from the binary's own `--help`: `--instance|-I N   set instance of SITL (adds 10*instance to all port numbers)`. Instance N's TCP MAVLink port (what `--drone-address=tcp://127.0.0.1:<port>` connects to) is `5760+10N`. Empirically verified: instance 1 bound `5770`, exactly as documented.

| Instance | PX4 `--drone-address` | ArduPilot `--drone-address` |
|---|---|---|
| 0 | `udp://:14540` | `tcp://127.0.0.1:5760` |
| 1 | `udp://:14541` | `tcp://127.0.0.1:5770` |
| 2 | `udp://:14542` | `tcp://127.0.0.1:5780` |
| N | `udp://:1454`+N (N<10) | `tcp://127.0.0.1:`+(5760+10N) |

`--sitl-instance` does **not** auto-derive `--drone-address` for you — pass both, matched, per the table above (consistent with every other option in this harness: nothing else is auto-derived either, e.g. `--px4-model`).

Two ArduPilot instances follow the same shape with `--sitl-instance=N` and `--drone-address=tcp://127.0.0.1:`+(5760+10N); `--ardupilot-sitl`/`--ardupilot-model` are unaffected by instance number (each instance still gets its own per-model, and now per-instance, working directory — see below).

**Verified working end-to-end**: launched PX4 instance 0 and instance 1 concurrently against `tests/mission/nav_takeoff/test_protocol.py` — instance 0 completed cleanly (22 passed, 3 xfailed) while instance 1 ran alongside it on its own ports and working directory, with no interference between the two.

### What changed under the hood, per fixture (`tests/conftest.py`)

- **`_manage_px4_sitl`**: at instance 0, the command line and working directory are byte-identical to before (`-s <rcS> -w <shared build dir>`, no `-i` flag — PX4 defaults to instance 0 regardless). At a non-zero instance, it passes `-i N`, the shared `etc/` directory as the *positional* `<rootfs_directory>` argument (not `-w`), and a fresh `build/px4_sitl_default/instance_N/` as `-w` — **this exact combination is required**; passing the shared rootfs only via `-w` breaks airframe lookup, because PX4 resolves `etc/init.d-posix/airframes` relative to `-w`'s directory *after* chdir'ing into it, regardless of the positional argument (verified empirically: without the positional-argument workaround, PX4 looks for `<instance_dir>/etc/...` and fails with "Unknown model"). Giving the positional argument makes PX4's own `create_symlinks_if_needed()` (`platforms/posix/src/px4/common/main.cpp`) auto-symlink `etc` inside the instance directory back to the shared one — confirmed by inspecting the resulting directory (`etc -> <shared>/etc`, plus a private `dataman`/`eeprom`/`log`/`parameters.bson`).
- **`_manage_ardupilot_sitl`**: `-I0` (hardcoded) became `-I{instance}`; the working directory and log filename get an `_iN` suffix for N>0 only, so two concurrent same-model instances (e.g. two ArduCopters) don't collide on state.
- **Kill-on-startup steps, in both fixtures**: previously `pgrep -x <name>` matched (and killed) *every* process with that name, which would kill a concurrently-running other instance. Now `pgrep -xa <name>` (still exact-name matching — never matches our own pytest process, whose argv happens to contain `--px4-sitl`/`--ardupilot-sitl`) additionally captures the full cmdline, which is parsed for the `-i`/`-I` argument and compared against `--sitl-instance` before killing — a different instance is left alone.
- **`_clear_stale_mavsdk_servers`**: same problem, same fix — now parses `-p <port>` from each `mavsdk_server` process's cmdline and only kills ones bound to *this session's own* computed ports, **all three** offset by `10*instance` (`GCS_GRPC_PORT`, `DRONE_GRPC_PORT`, `PAIRED_GCS_GRPC_PORT`). The paired-mode ports being un-offset was an initial design mistake, not a deliberate choice — see the caveat below for how it was found.
- **`paired_drone_server`/`paired_gcs_server`**: also offset by `10*instance` now, for the same reason as the standalone ports above — these fixtures start **unconditionally every session**, standalone included (`gcs_mavsdk_server` depends on `paired_gcs_server` in its own signature regardless of `--drone-address`), so two concurrent standalone sessions on different instances collided on these fixed ports even though neither was in paired mode. Confirmed by a real collision (2026-09-15): running PX4 instance 0 and ArduPlane instance 1 concurrently, PX4's session errored at setup entirely (`paired_drone_server` failed to bind port 50052, already held by ArduPlane's own concurrently-starting session) while ArduPlane's own run completed normally. `GCS_MAVLINK_PORT` (the paired loopback UDP port) is offset the same way.
- **`_clear_px4_if_paired`**: only kills instance-0 PX4 now (the only instance whose default ports actually conflict with the paired mock loopback) — a concurrently-running non-zero instance is left alone.
- **`gcs_mavsdk_server`** (standalone branch): binds its local mavsdk_server to `GCS_GRPC_PORT + 10*instance` instead of the fixed `50051`, so two concurrent pytest processes each get their own gRPC port too, not just their own MAVLink port.

### Known caveat (pre-existing, not introduced by this work)

While validating this, `pytest tests/mission/ -q` (the *full* mock-mode suite, no `--drone-address`) was found to hang intermittently during session-scoped fixture setup — confirmed via repeated A/B testing that the **unmodified pre-multi-instance code hangs at the same rate** (roughly 50% of attempts, in this environment, today), so this is pre-existing flakiness in the shared mock-mode startup chain, not a regression from the changes above. It's a different, deeper manifestation of the same family future-work item #8 already documents (full-suite resource accumulation) — worth a closer look some day, but out of scope here since it's unrelated to real-SITL/standalone multi-instance running (which is what this section is about, and which tested reliably throughout). Single-file and per-directory mock-mode runs were reliable in every trial.

### Future work: running the test *suite* itself across multiple instances, in parallel

What's built so far makes concurrent instances *possible* (you can hand-start N pytest processes against N instances, as the worked example above does) but doesn't yet make the *suite* parallel in one command. To get there:

1. **Shard by vehicle type across instances** — the natural first cut, since this project already runs each vehicle type as its own `pytest` invocation (`--vehicle-type=quadcopter` vs `fixed_wing` vs …) with its own log file. A thin driver script could launch, e.g., PX4 MC on instance 0, PX4 FW on instance 1, ArduCopter on instance 2, ArduPlane FW on instance 3, all in parallel, each with matched `--sitl-instance`/`--drone-address`/`--px4-model`/`--ardupilot-model`, and wait on all of them — turning today's serial "run one, wait ~5-10 min, run the next" pattern (used throughout this session) into one parallel batch. No new pytest machinery needed, just an orchestration script around the CLI surface that already exists.
2. **Shard *within* one vehicle type's test file** — splitting, say, `nav_takeoff/test_flight.py`'s 15 tests across 2-3 concurrent instances of the *same* vehicle/stack would need `pytest-xdist` (`-n auto`, `--dist=loadgroup` or similar) with each xdist worker mapped to a distinct `--sitl-instance`/`--drone-address` pair — not yet wired up; xdist doesn't know about SITL instances today, so every worker would currently fight over instance 0's ports. Needs a `pytest_configure`/fixture hook keyed off `os.environ.get("PYTEST_XDIST_WORKER")` to auto-select `--sitl-instance` per worker instead of requiring it on the command line.
3. **Resource ceiling, unknown** — future-work item #10 already documents a sandbox-level resource limit (not visible via `/proc/meminfo`) that killed even a single VTOL Tier 2 flight test in this environment. Running N concurrent instances is more likely to hit whatever that ceiling actually is, not less — before committing to (1) or (2) at any real scale, validate headroom empirically (e.g. try 2 instances of the heaviest test file before assuming 4+ works), rather than assuming CPU core count (24 in this environment) is the only constraint.

## Design decisions

1. **JSON plan files, not QGC format** — maps directly to MISSION_ITEM_INT fields; QGC adds abstraction layers that hide raw values.

2. **mission_raw over mission** — `mission` only supports flight plans and abstracts away mission_type, geofence, and rally points.

3. **Function-scoped System objects, session-scoped processes** — `gcs_mavsdk_server` / `drone_mavsdk_server` are session-scoped; `gcs_system` / `drone_system` are function-scoped to avoid gRPC channel / event loop conflicts across tests.

   **Exception — frame-type tests**: 65 tests would exhaust gRPC resources (~35 open channels).
   Uses `@pytest_asyncio.fixture(scope="class", loop_scope="class")` + `@pytest.mark.asyncio(loop_scope="class")` to share one `System` per class (4 total).
   Teardown is in a `try/finally` block inside each test to avoid event-loop mismatch.

4. **TRANSFER_TIMEOUT_S = 30 s** — Conservative upper bound for a 4-item plan over loopback including gRPC overhead.

4a. **gRPC stream cancellation** — `asyncio.wait_for` on a gRPC `async for` loop blocks indefinitely after timeout (the gRPC stream doesn't yield to asyncio cancellation).
**Fix**: fire-and-forget `asyncio.create_task` for the subscription; await only a plain `asyncio.Event` (set by the task on success).
Cancel the task without awaiting it.
Implemented in `_wait_for_connection` and any helper that cancels a gRPC subscription task.

4b. **PX4 SIH SITL readiness** — Two pitfalls: (1) PX4 writes `"INFO  [mavlink]"` with two spaces — searching one-space form silently misses all iterations.
(2) The `pxh>` prompt refresh loop grows the log file at several GB/min after startup — read at most 64 KB.

4c. **Verify the SITL binary against source before trusting a source reading** — a PX4 source file can be *ahead* of the built `bin/px4` binary in this environment (e.g. a fix landed in a previous session's git history but the binary was never rebuilt). If a test's observed behaviour doesn't match what the source appears to say, compare `stat -c '%y' <file>` against the binary's build timestamp and `git log -1 -- <file>` before concluding the source reading is wrong. Rebuilding (`make px4_sitl_default` in the PX4-Autopilot checkout) is a normal, expected step when this happens — it's a fast incremental build for a one-file change (a few minutes). Discovered building `tests/mission/condition_gate/`: a mask-table fix committed by an earlier session hadn't been rebuilt, and every gate upload failed with `INVALID_PARAM5_X` until it was.

5. **asyncio.timeout() over asyncio.wait_for()** — Python 3.11+ timeout context manager used where available.
   Replace with `asyncio.wait_for(..., timeout=t)` for 3.10 compatibility.

6. **GCS paired identity: sysid=255, compid=1** — MAVSDK only fires "System discovered" when it sees compid=1.
   Using compid=190 (MAV_COMP_ID_MISSIONPLANNER) means the drone's gRPC port (50052) never opens and `System.connect()` hangs indefinitely in `channel_ready()`.

7. **`collect_incoming_mission()` workaround** — MAVSDK-Python v3.15.x bug: `mission_raw_server.incoming_mission()` discards the plan when result=SUCCESS.
   Use `collect_incoming_mission()` in `tests/mission/conftest.py` (calls raw gRPC stub `SubscribeIncomingMission` directly) until fixed upstream.

5. **PX4 geofence relative-altitude frame z conversion** — `TestGeofenceFrames` fails for frames 3 and 6: PX4 accepts both but stores as frame=5 without converting z.
   Needs investigation: (a) is z conversion required by spec for geofence?
   (b) if so, this is a PX4 bug to report upstream.

6. **DO_SET_MISSION_CURRENT mission-item-change verification** — confirm the command actually moves the current mission item by subscribing to raw `MISSION_CURRENT` (msg id 42) via `mavlink_direct` before/after two different `param1` sends and asserting the emitted `seq` changes accordingly.
   Needs a `MockFlightStack` extension (current-seq tracking + `MISSION_CURRENT` emission, analogous to `emit_gps_global_origin`) to run in mock mode; see `tests/command/do_set_mission_current/README.md` § Design: verifying that DO_SET_MISSION_CURRENT changes the current mission item.

7. **ArduCopter SITL cannot complete initialisation in this environment** — `is_armable` never goes true; gyro/accel/mag `calibration_ok` telemetry flags stay `False` indefinitely (confirmed via direct `telemetry.health()` probe out to 40s+); the SITL console log stalls at `Waiting for internal clock bits to be set (current=0x00)` shortly after connection.
   Confirmed identically on three independent builds: the prebuilt `~/ardu_sitl/arducopter` binary, a fresh build of ArduPilot master, and a fresh build of the latest stable release (`Copter-4.6.3`) — the latter two launched via the officially-recommended `Tools/autotest/sim_vehicle.py`, not a raw binary invocation.
   Since a stable release fails the same way as a same-day development build, and PX4 SITL flight is confirmed working fine in the same environment, this looks like an environment-specific issue (not an ArduPilot bug, not a launch-method issue) — root cause not yet identified; further progress needs lower-level debugging (`strace`/`gdb`) not currently available (no `sudo`).
   Blocks `tests/command/do_set_mission_current/test_flight.py::test_param2_resets_jump_counter` (and any other Tier 2 flight test) on ArduCopter until resolved — Tier 1 (ACK-only, no arming) tests are unaffected.
   See `tests/command/do_set_mission_current/README.md` § ArduCopter SITL boot issue for full detail.

8. **Full-suite (`pytest tests/`) resource accumulation at current scale** — confirmed 2026-09-13: at ~345 total tests, a single combined session reliably starts erroring (`_wait_for_connection` timeouts) partway through `tests/mission/test_mission_client.py`, near the end of the run. The exact same tests pass cleanly when `tests/mission/` is run on its own (verified twice, identical 147 passed/10 skipped/2 xfailed both times), and `tests/command/` alone also completes cleanly (109 passed/53 skipped/22 xfailed, plus one flaky unrelated failure — see below) — so this is resource accumulation (function-scoped `System`/gRPC channels, per design decision #3's already-documented mechanism for `test_frame_types.py` alone) over one very long session, not a code defect. Until the client-test fixtures are revisited for this scale, run `tests/command/` and `tests/mission/` as two separate `pytest` invocations for a clean local run — see root `README.md`.

9. **`do_set_global_origin::test_do_set_global_origin_gps_global_origin_emitted` flakiness** — confirmed genuinely flaky (2026-09-14): running it in isolation repeatedly produces PASS, FAIL ("GPS_GLOBAL_ORIGIN emitted 2 times; expected exactly 1"), PASS across three consecutive runs — a real intermittent race, not a one-off fluke or a regression from any particular change. Likely the same family of timing race as the already-documented AUTOPILOT_VERSION dual-response / duplicate-ACK issues elsewhere in this file. Treat a single failure of this test as expected background noise, not a signal to investigate, unless it starts failing consistently.

10. **PX4 VTOL Tier 2 flight tests cannot complete in this environment (2026-09-14)** — `tests/mission/nav_takeoff/` against PX4 v1.17.0, `--vehicle-type=vtol --px4-model=sihsim_standard_vtol`, is blocked: even a single Tier 2 test (`test_takeoff_implicit_from_waypoint` alone) gets killed by a "low memory" signal, reproduced 5 times in a row (both the full nav_takeoff suite and an isolated single test). Two real, now-fixed bugs were found and ruled out along the way, neither of which is the actual blocker:
    - A `.clear()` bug in `tests/flight_helpers.py`'s Tier 2 auto-logging (`_write_tier2_module_log`) wiped all accumulated results after every single test — fixed; verified the full results table now persists correctly (see design pattern #7 above).
    - PX4's own `pxh>` console-prompt spam (already documented in design decision 4b for the 64 KB *readiness-check* read) can grow the SITL console log at 10s of MB/sec once a GCS is connected and driving activity — confirmed via a standalone PX4-only test this does NOT reproduce without MAVSDK/pytest attached, so it's specific to the connected/flying scenario. Fixed with a background watchdog thread in `_manage_px4_sitl` (`tests/conftest.py`) that caps the file at 5 MB, `SIGSTOP`-ing the PX4 process for the handful of syscalls needed to truncate+reposition atomically (a naive truncate-then-reseek without stopping the process races PX4's own writes and can still balloon to 1+ GB — see the code comment for the concrete failure mode observed). Verified working: PX4's console log stayed bounded in the low single-digit MB range through every subsequent attempt, confirmed via both file-size sampling and full `/proc/meminfo` sampling every 0.5 s through an entire run.
    - With both of those fixed, the kill still happens, at a consistent point (right after arming, during the initial climb/transition). Direct `/proc/meminfo` sampling (`MemAvailable`) through the full duration of the last attempt shows it staying flat around 8.6 GB the whole time, including the sample immediately before the kill — and the kill took out the independent monitoring process alongside the test run. This means the constraint is not host-wide memory pressure as reported by `free`/`/proc/meminfo`; it appears to be a sandbox/harness-level resource limit on this session's background processes that isn't visible from inside the sandbox. Not reproduced for MC (`sihsim_quadx` completes cleanly: 29 passed, 7 xfailed, 0 failed) — whatever this is, it is specific to VTOL, or at least does not reproduce at MC's resource footprint.
    - Workaround: none identified yet from inside the sandbox. Try again in a session with more headroom (fewer concurrent processes/sessions on the host), or investigate the harness-level limit from outside the sandbox. MC and (once tested) fixed-wing are unaffected.
    - **2026-09-15 update — the resource-limit kill did NOT reproduce this time (different failure mode found instead)**: re-ran the same suite against a fresh v1.17.0 release build; no kill this time (`--sitl-instance`/watchdog work since 2026-09-14 may have helped, or it's simply not deterministic). Every flight test still failed, but for a different, more specific reason: `_wait_armable()` consistently timed out at 60s. A direct, harness-independent MAVSDK probe against the same binary showed `is_armable` actually goes true almost instantly (~1s) — so the *connection/arming* path itself isn't slow. Following up with a hand-built upload→arm→start_mission→mission_progress probe (same shape as `_fly_to_altitude_target`, plus PX4's own `test/mavsdk_tests/autopilot_tester.cpp`'s documented "PX4 needs time to realize it has a mission" 1s post-upload sleep, added defensively): mission uploads and starts fine (`mission_progress` correctly reports `current=0`), but altitude stays at flat 0.0m for 160+ seconds — the vehicle never actually leaves the ground. Checking `armed()`/`flight_mode()`/`landed_state()` directly on the stuck vehicle: `ARMED: False`, `FLIGHT_MODE: HOLD`, `LANDED_STATE: ON_GROUND` — PX4 auto-disarmed itself back into HOLD at some point, having never attempted to climb. This looks like a genuine VTOL-specific PX4 arming/takeoff gate distinct from MC/FW (neither of which has ever shown this) — plausibly related to no RC/manual_control input being sent (none of this harness's flight helpers send RC input for any vehicle type, so if VTOL's mission-takeoff path specifically requires it while MC/FW's don't, that would explain the asymmetry) — not yet confirmed against source. Superseded the low-memory-kill theory as the *current* blocker (that may still be real and just didn't trigger this run); the practical status is unchanged (VTOL Tier 2 still doesn't produce usable flight data in this environment) but the lead is more specific now for whoever picks this up next: check PX4's VTOL takeoff/arming source for an RC-presence gate, or try sending sustained neutral `manual_control` input alongside the mission the way `autopilot_tester.cpp`'s `fly_forward_in_posctl()` does for its own (non-mission) manual tests.
    - **The RC-presence hypothesis was tested directly against PX4 fixed-wing (`sihsim_airplane`, non-VTOL) and did NOT fix it** — same "arms, mission starts, altitude stays flat at 0.0m" symptom as VTOL, confirmed 2026-09-15 against a hand-built probe feeding sustained neutral `manual_control` input throughout (mirroring `fly_forward_in_posctl()`) — no climb within 60s either way. So this isn't simply "VTOL needs RC": the same never-leaves-the-ground behaviour reproduces on plain fixed-wing too, and this particular mitigation doesn't help (though `manual_control` is only actioned in a manual-control-compatible mode, so this doesn't cleanly test the hypothesis while in AUTO.MISSION — it rules out this specific attempt, not the underlying idea). One partial, confounded clue: `armed()`/`flight_mode()` checked on the stuck fixed-wing instance afterward showed `ARMED: True`, `FLIGHT_MODE: RETURN_TO_LAUNCH` (unlike VTOL's `ARMED: False`/`HOLD`) — but that check ran after the manual_control-feeding probe, so it's confounded by that input, not a clean read of the undisturbed failure. This answers the user's own explicitly skeptical framing directly ("arming when the vehicle has a mission loaded with a takeoff command should also work — emphasis on should"): confirmed, it does not, for either PX4 airframe, in this environment. Root cause still open — a clean next step (not done here, time-boxed) is a fresh, undisturbed probe with STATUSTEXT/EXTENDED_SYS_STATE subscribed from the start and zero manual_control input, to capture PX4's own stated reason (if any) for never proceeding past the takeoff item.
    - **Workaround for unblocking *other* mission-item tests on these frames (2026-09-15, user's call)**: PX4 fixed-wing/VTOL Tier 2 tests for commands other than NAV_TAKEOFF itself (e.g. `condition_gate`) don't need to get airborne via a mission-item NAV_TAKEOFF — a commanded takeoff (`action.takeoff()`, i.e. MAV_CMD_NAV_TAKEOFF sent as a COMMAND_INT/LONG rather than uploaded as mission item 0) is a different PX4 code path and may not share this blocker. If it works, it becomes the standard "get airborne" precondition for non-NAV_TAKEOFF Tier 2 tests on these two frames specifically (MC/ArduPilot frames have no need for it, since mission-item NAV_TAKEOFF already works there). This doesn't resolve the open question above — NAV_TAKEOFF-*as-a-mission-item* on PX4 FW/VTOL is still unexplained — it just avoids blocking unrelated test work on it.
    - **2026-09-16 — implemented and validated, on PX4 MC (not yet on FW/VTOL, since `condition_gate` has never targeted those frames)**: `_takeoff_via_command()` added to `tests/flight_helpers.py`, adopted by `tests/mission/condition_gate/test_flight.py` (see its own CLAUDE.md's dated section). Two real PX4 MC runs confirm the mechanism itself works and doesn't change the tested command's behaviour — geometry/timing matched the pre-swap baseline exactly. What's still unverified is the actual motivating case: whether this commanded path *also* avoids PX4 fixed-wing/VTOL's "arms, mission starts, never leaves the ground" issue — that needs a real FW/VTOL run of a mission-item Tier 2 test using this helper, not yet attempted.
